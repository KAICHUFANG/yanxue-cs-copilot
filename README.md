# 山海科普 · 客服助手

给研学项目私域客服用的内部工具：**输入家长的问题，输出可以直接复制发出去的回答或文案**，并标注数据来源、提示哪些话不能自动发。

> 不是给家长用的聊天机器人。C 端机器人要求家长改变习惯（多打开一个应用），落地率很低；
> 内部工具只改变客服的工作流程，当天就能用起来。

---

## 它解决什么问题

研学活动运营中，客服每天重复处理四类事情：

| 场景 | 原来的做法 | 现在 |
|---|---|---|
| 家长问价格、时间、名额、适合几岁 | 翻推文、翻聊天记录、问负责人 | 一句话查到，并说明「以当期推文为准」 |
| 每期写活动群文案（欢迎、提醒、结束感谢） | 每次重写一遍，容易漏字段 | 按当期数据自动填充，只留需要人工判断的空 |
| 进校预约引导 | 手找文案、手找图、手找公众号名片 | 给出**四件套发送包**，并标出哪几件必须手动发 |
| 推文里没有的信息（集合点、是否分组） | 事后想起来才去问 | **每次补充后自动提示「这期还缺什么」** |

## 能做什么

### 1. 活动问答

```
👤 第十六期多少钱？
🤖 第十六期是阶梯同行价：单人 88 元/人，两人同行 78 元/人，三人同行 68 元/人，
   含课程设计、场地、物料、饮用水和研学专项保险。以当期推文为准。
```

知识库里没有的期次会如实说「没有记录」，**不会拿别期的数据顶替**。

### 2. 活动群文案自动填充

```
👤 帮我写第十六期的活动群文案
🤖 已能直接发的：① 建群当天欢迎语（活动时间、地点、对象已自动填入）
   还缺：集合时间、集合地点 —— 需要向活动负责人确认
```

### 3. 补录信息

```
👤 第十六期集合时间是14:40，集合地点在海南大学北门
🤖 ✅ 已记录并备份。这一期还缺：室内还是室外、是否分组、每组人数
```

### 3.5 换期：直接粘下一期推文

一期办完，把新一期的推文整篇粘进来就行，不用清空任何东西：

```
👤 （粘贴第十七期推文全文，两千多字）
🤖 已按「第十七期」整条替换写入成功，推文未提及的字段已清空——
   这是有意为之，并非出错，待向负责人确认后再补。
```

**为什么是「整条替换」而不是「只覆盖推文里写到的」**（这是真实报过的 bug）：

推文里通常**没有**集合地点、集合时间、名额数字、室内外、分组人数——
这些是客服事后手工补的。如果换期时只覆盖推文提到的字段，
新一期就会静默继承上一期的「五教104」「25 人」「室外」，
客服照着答家长，答的是另一期的事，而且**从界面上完全看不出来**。

所以：

| 情况 | 判定方式 | 存储行为 |
|---|---|---|
| 粘的是另一期的推文 | 代码比期次（`第十五期`≠`第十六期`），模型 `is_new_activity` 兜底 | **整条替换**：以空白记录为底，只留抽到的字段，其余清空 |
| 同一期的补充/更正 | 期次相同 | **合并**：只覆盖这次提到的字段 |
| 单句改字段 | 不是整篇文章 | **合并** |

被替换掉的旧记录进 `data/archive/superseded.jsonl`（一行一条），
旧推文原文进 `data/archive/article_<期次>.md`，
再加上 `data/backups/` 的整文件快照 —— 三层都能翻回去。

### 4. 进校预约定稿 + 发送包

返回四件套，并明确标出**系统给不了、必须客服手动发**的项：

1. 预约提醒文案（可复制）
2. 「海南大学」公众号名片 ← 系统无此链接，必须手动发
3. 进校预约填写示例截图 ← 必须手动上传
4. @所有人 催办话术（可复制）

这四件会**直接排进「阶段② 进校预约」的输出里**（加上门禁提醒共 5 条，按发送顺序），
不需要客服再去查一次流程——流程定稿只存在 `processes.json` 一处，群文案用 `uses_process` 引用它。

### 4.5 收尾文案：按原文拟稿，客服只核对

「结束感谢」里的现场亮点、「回顾分享」里的具体细节，过去是留给客服自己想的两句空。
现在由系统从原文拟初稿：

```
👤 写结束感谢
🤖 🌿【山海科普｜「自贸港小商人·集市大冒险」圆满结束】
   ……
   今天孩子们分组扮作五类小商人，掷骰走棋盘，走完生产、加工、买卖、合伙、交货全过程，收获满满～
   ……
   🤖 下面这几处是系统按原文拟的稿，发之前核对一下现场是不是真这样：
   · 现场亮点：「分组扮作五类小商人，掷骰走棋盘，走完生产、加工、买卖、合伙、交货全过程」
     依据当期活动推广推文：「分组扮作五类小商人，掷骰走棋盘，在三个小时里走完生产……」
```

三道闸保证它不编：

| 闸 | 做法 |
|---|---|
| 只给原文 | 只用推文原文当资料，不塞别的上下文 |
| 要它交依据 | 输出「依据的原句」，**这句必须在原文里找得到**（去空白标点后子串匹配），找不到整条作废 |
| 拟稿要标注 | 输出里单独标「系统拟的稿」+ 依据原句，客服看得见才核对得上 |

找不到依据时宁可留占位符，也不硬写。

**活动回顾推文要单独存起来**：把回顾推文全文粘进对话框，会存到
`data/articles/reviews/review_<期次>.md`。它**不跟着换期消失**——
活动记录每期都被整条替换，回顾推文是历史资料，客服两个月后问「上一期回顾里写了什么」还得能查回来。
存回顾推文**不动任何活动字段**（回顾里全是上一期的旧值，抽了就串期）。

### 5. 缺口体检

```
👤 这次活动还缺什么信息
🤖 目前还缺 5 项：集合地点、集合时间、室内还是室外、是否分组、每组人数
   这几项需要向活动负责人确认。
   另外三项是活动前后再补的：导航照片、真实亮点、回顾推文链接
```

### 6. 评测：能测出「它答错了」

LLM（大语言模型）应用最容易骗人的地方是 demo：挑几个好问题，看起来都对。
所以这个项目自带一套评测，跑一次约 40 秒、成本不到 1 毛钱。

```bash
python eval\run_eval.py                            # 回归集 29 条
python eval\run_eval.py --file cases_real.json    # 真实家长问法 22 条
python eval\run_eval.py --file cases_hard.json    # 难题集 14 条
python eval\write_tests.py                        # 录入回归 18 条
```

**四维打分**（一条用例要同时满足前两个维度才算通过）：

| 维度 | 查什么 | 为什么单独立这一维 |
|---|---|---|
| 路径选对 `tool_ok` | 该走确定性路径的走了没（写库 / 填文案） | 该写库的没写进去，答得再漂亮也没用 |
| 关键事实齐全 `facts_ok` | 回答里有没有该有的硬数据 | 价格、时间这类必须逐字出现 |
| 命中正确说法 `any_ok` | 说到了正确的口径 | 抓住「答了但答偏」 |
| 无编造 `clean_ok` | 没有出现禁止的说法（正则黑名单） | 拒答和编造是两个反方向，必须分开测 |
| 可直接发家长 `voice_ok` | 有没有夹带系统腔（资料库/界面/面板/我让客服…） | README 里的产出是**客服要发给家长的话**，出现系统词就发不出去 |
| 长度合规 `len_ok` | 有没有超过用例声明的字数上限 | 朋友圈超过 6 行会被折叠成「全文」，写太长等于没发出去 |

**当前结果**（`temperature=0`，DeepSeek `deepseek-chat`）：

| 用例集 | 通过率 | 说明 |
|---|---|---|
| 回归集 `cases.json`（29 条） | 29/29 | 覆盖查询、规则、进校、文案、录入、编造检测 |
| 真实问法 `cases_real.json`（22 条） | 21–22/22 | 其中 10 条来自真实聊天记录 |
| 难题集 `cases_hard.json`（14 条） | 14/14 | 情绪、模糊指代、编造诱饵、家长记错 |
| 录入回归 `write_tests.py`（18 条） | 18/18 | 该写的写了、不该写的没写、换期该清的清了 |

录入回归里 11 条是**不走模型**的纯代码检查（`store_replace_tests()`）——
「换期时没提到的字段必须清空」这条纪律不能靠模型心情，
所以直接调 `store.update_activity(replace=True)` 断言磁盘结果。

**分数会抖**：同一批题连着跑，总有一条左右摇摆（21 或 22）。
原因是模型输出措辞偶尔变化，正好没撞上断言里的词——**不是回归，是断言太窄**。
真要稳定得靠判定更宽松或多次取多数，目前没做，就先如实记着。

**关于这两个数字的真实性，得说清楚：**

1. 真实问法里的那 10 条来自**真实家长聊天记录**，没有参与任何调参。第一次跑的成绩是 **7/10 = 70%**，
   3 条失败暴露了真问题（车辆进校被当成「每人预约」、迟到规则没讲到「不等人」）。
2. 修完之后才是 10/10。但**这时的 10/10 已经不算干净的留出集了**——我看过失败用例再改的，
   属于「测试集污染」。真实的泛化能力更接近第一次的 70%。
3. 所以结论不写「准确率 100%」，而写：**首轮真实盲测 70%，修完 100%（已污染）**。
   下一步是攒第三批没见过的真实问题。

**踩过的坑（都已修复，留作记录）：**

- 子串假阳性：断言 `["18"]` 命中了 `15:00-18:00`；`["接龙"]` 命中了「不是在群里接龙」。
  判据必须写完整短语，禁用词要单独用正则黑名单。
- 评测写坏生产库：自动化用例往真实 `activities.json` 里写了假数据。
  现在 `run_eval.py` 先把知识库复制成副本，用 `ACTIVITIES_FILE` 环境变量指过去，跑完不碰真数据。
- 修 A 崩 B：往「政策类关键词」里加「怎么报名」，导致「第十期怎么报名」不再如实回答「没有第十期记录」。
  （那套探针已经随路由层一起删掉了——现在没有 `auto` 这个概念。）

## 客服工作台（`启动工作台.bat`）

界面用 **Streamlit**（Python 的 Web 界面框架）。之前是手写 tkinter，每加一个交互都要自己算布局、
也没法边生成边显示。换框架之后拿到的三样东西：**逐字流式输出**、**文本块自带复制按钮**、
**浏览器打开（将来放服务器上就能远程用）**。旧 tkinter 版保留在 `app_workbench.py`，双击 `备用_旧界面.bat` 可回退。

```
┌────────────────────────────────┬──────────────────────┐
│                                │ 当前活动  第十六期 ▾  │
│  家长：集合地点在哪里？          │ ──────────────────── │
│  ─────────────────────────     │ ★✓ 活动日期  10-24    │
│  【发给家长】                   │ ★✓ 活动时段  15-18    │
│  这一期集合点还没有记录…         │ ★✗ 集合地点  —        │
│                                │ ★✗ 集合时间  —        │
│  客服：这期是室外，每组4到5个     │ ★✓ 室内室外  室外      │
│  ─────────────────────────     │ ★✗ 是否分组  —        │
│  ✎ 已写入：indoor_outdoor、     │ ★✓ 每组人数  4-5人     │
│           group_size           │ ...                  │
│  【回复】已写入第十六期…          │ 还缺 3 项             │
│                                │ ──────────────────── │
│  [输入框：所有输入都在这里]       │ 客服提示（不发给家长）  │
│  [发送] [复制] [清空]            │ · 集合时间需向负责人…   │
└────────────────────────────────┴──────────────────────┘
```

**设计决定：状态栏是独立栏位，不随对话滚动。**

用 `position: fixed` 钉在视口右上角（宽屏时左侧对话列自动让出 377px）。
先试过 `position: sticky`，不行：它只能在父容器高度内停泊，对话滚到底时面板会被顶出屏幕
（实测 top 变成 -130px）——而那正好是客服看最新消息时最需要它的位置。
给父容器加底部留白也无效：留白让可滚动区同步变大，钳制位置 1:1 跟着跑
（留白 0/160/320/480/640px → 面板 top -130/-290/-441/-601/-761）。
最终 fixed + 不透明底色（`prefers-color-scheme` 兜深色主题），
滚到 0/700/1500/9339 时面板 top 恒为 58px。窄屏（<1000px）不启用，交给 Streamlit 堆叠。

**设计决定：所有输入都走对话框，状态面板只读。**

不让客服学表单，是因为她们本来就在微信里打字，多一个窗口就是多一道负担。
但「这是录入还是提问」的判断又必须做——所以不靠判断准，靠**结果可见**：

- 写库仍然过 `store.update_activity()`：字段白名单 → 类型校验 → 写前自动备份
- 写完立刻在左边显示「✎ 已写入：xxx」，右边状态面板当场刷新
- 写错了马上看得见，也能从 `data/backups/` 回滚

**文案分两类，执行方式不同：**

| 类型 | 例子 | 谁做 | 为什么 |
|---|---|---|---|
| 定稿模板 | 欢迎语、进校预约提醒、活动提醒、出发提醒、结束感谢 | 代码填模板 | 有定稿，必须原文输出，不能让模型润色 |
| 现写推广 | 私域群推广、朋友圈 | 模型写 | 本来就没有定稿，事实取自资料，写法自由 |

推广文案按渠道分两种长度：**微信群 150-250 字**（屏幕能滚，可以分点讲清楚）；
**朋友圈 60-100 字、最多 5 行**（超过 6 行会被折叠成「全文」，家长根本不会点开，所以不许分点罗列）。

**状态面板由代码算，不由模型算。** 实测过：问模型「现在信息齐了吗」，
它会把「有值但可疑的集合时间」算成缺口，同时漏掉真正缺的「是否分组」「每组人数」。
所以缺口的答案只信 `store.missing_fields()` 读磁盘的结果——**模型负责说话，代码负责说真话**。

## 换 Key / 换模型（不用改文件）

界面最上面有一个 **🔑 API 设置** 折叠面板，五个字段 + 一个「保存并测试连接」按钮：

| 字段 | 填什么 | 不填会怎样 |
|---|---|---|
| API Key | 你自己的 Key（留空 = 不修改现有） | 整页提示「未找到 Key」并停住 |
| 接口地址 | 默认 DeepSeek；换别家填它的 OpenAI 兼容地址 | 填错 → 保存后报「连不上」 |
| 模型名 | 默认 `deepseek-chat`，必须和接口配套 | 填错 → 保存后报「连不上」 |

点按钮会做三件事：写回 `.env`（先备份 `.env.bak`）→ 重建模型客户端 → **真发一次最小请求**验证连通。
通过会提示「已保存，连接正常」；不通过会说清是 Key、地址还是模型名的问题。

> 为什么要真发一次请求：Key 填错、`base_url` 少 `/v1`、模型名和接口不匹配，
> 这三种错误都只在真调用时才暴露。存完不测，等于把错误留给客服。

## 界面布局（客服端）

```
┌─────────────────────────────────────────┬──────────────────────┐
│ 🔑 API 设置   （折叠）                   │                      │
├─────────────────────────────────────────┤   当前活动 + 缺口    │
│                                         │   （固定，不随对话滚）│
│  对话（消息列表）                        │                      │
│                                         │                      │
│  ┌───────────────────────────┬────────┐ │                      │
│  │ 输入框（在对话这一栏里）     │  发送  │ │                      │
│  └───────────────────────────┴────────┘ │                      │
│  [清空对话] 本次会话 N tokens  ☑客服提示 │                      │
└─────────────────────────────────────────┴──────────────────────┘
```

三个曾经踩过的坑（都已修）：

| 问题 | 原因 | 修法 |
|---|---|---|
| 「清空对话」被输入框盖住 | 用的是全宽的 `st.chat_input`，固定在页面底部，横跨整个宽度压住右栏 | 换成**左栏内的表单**（文本框 + 发送按钮），对话相关的按钮都放回左栏 |
| 「API 设置」被顶部工具栏压住一部分 | `.block-container` 的 `padding-top` 只有 2rem，而 Streamlit 工具栏浮在页面顶部 | padding-top 改 4.2rem，固定面板 `top: 4rem` |
| 明亮模式下右侧栏有一块不变白 | 底色原来靠 `prefers-color-scheme`（跟的是**系统**主题），用户在 Streamlit 里手动切成明亮时就不对；`st.context.theme` 也只给一个 `type`（实测明亮实例里仍报 dark，不可信） | 注入一小段 JS：量页面**真实背景色**写进 CSS 变量 `--panel-bg`，并监听主题切换（`MutationObserver` + 每 1.2s 兜底） |

## 使用记录（谁问了什么、系统答了什么）

**只落文件，不进界面。** 工作台是客服干活的地方，日志是复盘用的东西，
放在一起既占地方、又让人不知道该看哪个（用户明确要求：记录不要放在面板里）。

文件：`data/logs/chat.jsonl`，一行一条，**永久保留、全量、回答不截断**：

```json

 "q": "家长电话 139****1111 打不通",

 "trace": "classify → update_activity", "wrote": ["meeting_point"],

```

## 几个关键设计决定

### ① 确定性的事交给代码，不确定的才交给模型

实测发现 DeepSeek 会忽略 `tool_choice` 的强制指定（问「第十六期多少钱」它会去调 `list_activities`）。
而价格、名额这类字段**错一个数字就是事故**，不能靠概率模型决定「该查什么」。

所以分成两条路：

```
用户提问
  ↓
router.py（正则抽期次 + 关键词判意图）—— **已删除，见下文 ②**
  ├─ 能确定 → 代码直接执行工具 → 模型只负责组织语言
  └─ 不能确定 → 标准 Function Calling 循环
```

### ② 这套「规则路由太僵硬了吧」——我先用数据回答，然后把它删了

`router.py` 用关键词表判意图，最大的一条是**从问题里解析「第十六期」**。

这个设计是错的，而且是数据直接打脸的那种错：

| 问题来源 | 条数 | 里面提到期次的 |
|---|---|---|
| **真实家长聊天记录** | 10 | **0 条（0%）** |
| 我自己编的回归集 | 28 | 15 条（54%） |

群就是第十六期的群。家长只会问「多少钱」「几点集合」，**不会说「第十六期多少钱」**。
我编的回归集里那 15 条，是照着我自己的路由逻辑编的——拿它评测等于让代码在自己的考卷上考试。

**四个架构在同一批用例上的实测**（当时的脚本 `eval/ab_compare.py` 已随重构删除，数据留在这里）：

| 架构 | 做法 | 通过率 | 平均延迟 | 总 tokens |
|---|---|---|---|---|
| A 规则路由 | 关键词判意图 → 代码执行工具 | 28/28 | 1.46s | 74k |
| B 模型选工具 | 删掉 router，模型从 8 个工具里自己挑 | 25/28 | 2.33s | 148k |
| C 全量投喂 | 不用工具，知识库全文塞进上下文 | 22/28 | **1.15s** | 279k |
| D 读写分离 | 写入走工具，其余全量投喂 | 27/28 | 1.39s | 269k |

B 输得最值得看。它的问题在于**选错知识源之后开始圆场**，不只是选错工具：

```
家长：需要带身份证吗，我看要填身份证号
B   ：不用带身份证原件，报名表里填身份证号是为了买保险用的…
      ↑ 知识库里写的是「不需要，登记也不填身份证号」。它没查到，就编了个合理的理由。
```

### ③ 所以 v3 是这样：期次由界面给定，不从话里猜

把「猜」换成「给定」，路由整层就消失了：

```
当前活动 = S16（界面选中的那一期 / 群绑定）
        ↓
knowledge.build_context()  这一期的数据 + 全期概要 + 通用规则 + 流程 + 文案模板
        ↓
模型直接读这段上下文回答 —— 没有工具、没有意图分类、没有期次正则
```

**确定性功能不经过模型**：写入走 `store.py`（字段白名单 + 类型校验 + 写前备份），
文案生成走 `renderer.py`，缺口体检走 `store.missing_fields()`。
模型只干一件事：用给定资料回答家长的自然语言。

**结果**（当时的脚本 `eval/ab_real.py` 已删除，数据留在这里；现在用 `run_eval.py --file` 复现）：

| | 通过率 | 每条约 tokens |
|---|---|---|
| v2 关键词路由（284 行） | 23/23 | 约 2.6k |
| **v3 上下文直答（0 行路由）** | **23/23** | 7.1k |

打平。但 v3 少了 284 行路由代码、9 张关键词表、3 个期次正则，
以及那套「加一个词就踩坏另一个」的维护负担。

**代价要讲清楚**：v3 每条多花约 3 倍 token，而且不随规模扩展——
知识库现在 1.4 万字，到 30 期会撑爆上下文窗口。
那时唯一的解是 RAG（检索增强生成）。所以 v3 是当前正确的解，不是永久解。

> 完整复盘（错误怎么长出来的、三个根因、面试怎么讲）见 [`docs/踩坑复盘.md`](docs/踩坑复盘.md)。

### ④ 产出的是「客服发给家长的话」，不是系统在跟家长对话

这个工具是**给客服用的**：客服把家长的问题打进来，系统帮她想怎么回，她复制过去发出去。
家长永远不碰这个系统。

所以模型的输出必须是**客服口吻**：第一人称「我」= 客服本人，「您」= 家长。
一句话写错就发不出去：

| 错的 | 对 |
|---|---|
| 报名二维码在客服这边，我让客服发您 | 报名直接扫当期推文里的二维码就行，我发您一份推文 |
| 这一期我这边没有记录，建议看当期推文 | 这个我确认一下再回您 |
| 缺口由界面右侧显示 | （这句压根不该出现在发给家长的话里） |

系统自己的能力边界（看不到推文图片、没有家长名单、哪些东西必须客服手动发）
**不进正文**，进「客服提示」那一栏——那段不发给家长。

评测里有一条硬约束 `voice_ok`：家长问题的回答里不许出现
`资料库 / 知识库 / 界面 / 面板 / 右侧 / 我让客服 / 系统里`。
只有「客服在问工具本身」的用例（`voice: "meta"`）豁免。

### ④ 推文不拆字段，整篇给模型读

一开始我把推文拆成 `segments`（环节）、`awards`（奖项）、`learning_outcomes`（研学收获）这些结构化字段存进 JSON。
这是错的。

**推文是高自由度的叙述文字，每次的活动内容、排版、说法都不一样。** 硬拆成固定字段等于用一套不存在的结构去框它：

- 拆的过程中一定丢东西——措辞、语气、逻辑链条全没了
- 每来一期新推文就要重新拆一遍，还是一样会丢
- 写推广文案时最该复用的就是推文原文那套说法，拆成「环节1/环节2」正好把它毁了

**正确做法：只拆固定字段，其余整篇给模型。**

| 存成结构化字段 | 整篇原文放进上下文 |
|---|---|
| 价格档位、名额、日期时段、集合点、室内外、是否分组、每组人数、招募对象 | 活动定位、活动内容、环节机制、研学收获、专业支持、费用退费、自备物品、报名方式 |
| 因为**代码要拿它们做校验和计算**，不能有歧义 | 因为**它们是叙述文字**，拆了就失真 |

推文才两千多字，整篇塞进上下文一点都不贵。
客服粘一篇新推文时，代码把原文存到 `data/articles/current.md`，只抽固定字段进库——
**下一期不需要任何人手工拆解。**

**冲突时以谁为准**（写进了系统提示）：价格、名额、日期、集合点、室内外、分组、每组人数 → 固定字段（客服可能更新过）；
其余内容 → 推文原文。

### ④ 定稿文案原文输出，不让模型重写

进校预约文案、@所有人 话术这类内容有定稿，每次让模型「润色」一遍，词句会飘，客服也不敢用。
所以 `processes.json` 里标了 `output_mode: "verbatim"`，工具返回时附带硬约束：**只能原文输出，禁止改写**。

### ⑤ 缺失就留空，绝不推测

知识库里字段为空一律写 `null`，含义是「**查过，没有这个信息**」，而不是「没填」。
渲染文案时保留 `{{集合地点}}` 并列入未填清单——**留着空让客服去问，比填个半对的值安全**。

判断依据是：填了「是」会引出「几人一组」这个新问题，而答不上来更糟。

### ⑥ 敏感信息走环境变量

被访人姓名、手机号存在 `.env`（已 gitignore），`processes.json` 里只有占位符。
配置缺失时程序**不报错**——保留占位符并给出告警，保证别人 clone 下来能跑。

### ⑦ 写入必须可回滚

客服会陆续补字段。`store.py` 的做法是：字段白名单 → 类型校验 → **写前自动备份** → 写后返回「还缺什么」。
一个字段格式不对就整体不写，避免写一半。

**备份还不够，还要分清「补」和「换」。** 这是后来补上的（真实事故）：

`update_activity()` 原来只有一种写法——`target.update(accepted)`，也就是只覆盖这次给的字段。
这在「补信息」时是对的，在「换期」时是灾难：粘进新一期推文，推文没写到的
集合点 / 名额 / 室内外 / 分组人数全部留着上一期的值，新一期看上去字段齐全，
实际上每一项都可能是错的，而且**没有任何地方会报警**。

现在 `update_activity(..., replace=False)` 有两套语义：

```
合并   replace=False   只覆盖这次给的，其余不动        ← 同一期的补充/更正
替换   replace=True    空白记录 + 只留这次给的        ← 另一期的推文
```

`replace=True` 时额外做四件事，都是防「静默串期」的：
清空白名单外的一切（`capacity_text`、`_*_note`、`source`…）→
按新期次重算 `id`/`session_no` → 旧记录写进 `data/archive/superseded.jsonl` →
`status` 默认成「待确认」而不是继承上一期的「报名中」。

判定「这是不是另一期」用两路信号取并集：**代码比期次**（最可靠，期次是固定字段）+
模型的 `is_new_activity`（兜住推文没写期次的情况）。只有一路会误判，两路并集反而稳。

回归测试里既测端到端（粘一段推文），也单测 `store` 这一层（不走模型）——
后者是纯代码纪律，必须 100% 稳定，不能靠模型心情。

### ⑧ 调用翻了 3 倍，分数只涨了 0.05 —— 记账记在这

v3 之后我想再压一压效果，所以建了一套**难题集**（14 条，专挑 v3 覆盖不到的地方：
情绪化提问、模糊指代「那个几点啊」、编造诱饵「听说这次是张老师带队的？」、
家长记错日期、家长拿上一期经验来套这一期、超范围请求「帮我订个酒店」），
又加了一个 **LLM 裁判**（用模型当评审，四个维度打分，必须给理由）。

然后上了 v4 管线：**拆题 → 带引用草稿 → 代码校验引用 → 裁判复审 → 修订**。
其中第 ③ 步是硬校验：模型声称「我引用了原文」不算数，每个引用必须逐字在资料里找得到。

结果：

| | 正则层 | 裁判层 | 准确性 | 完整性 | 可直发 | 分寸 | 耗时 |
|---|---|---|---|---|---|---|---|
| v3 单次调用 | 14/14 | 14/14 | 4.71 | 4.43 | 4.93 | 4.64 | 1.3s |
| v4 五步管线 | 14/14 | 14/14 | 4.79 | 4.43 | **5.00** | 4.71 | 4.0s |

**结论：调用数 1 → 3.4，分数从 4.68 涨到 4.73。几乎没动。**

原因不是管线没用，是**天花板不在模型这边**：
知识库里有 5 个字段是 `null`（集合地点、集合时间、室内室外、是否分组、每组人数），
而这恰恰是家长问得最多的。再多的推理也推不出一个还没确定的时间。

### ⑨ 所以把预算花在了另一处：给客服的「内部提示」

既然模型嘴上说不出更多，就让它多说一层**不发给家长的话**（`pipeline.answer_v5`）：

```
家长：集合地点在哪里？几点集合？

已发给家长的回复：
这一期集合地点和集合时间我这边还没有记录，团队确定后会在活动群发定位和导航照片…

给客服的内部提示：
· 集合时间需向负责人确认后填入活动提醒文案，并在活动前一天晚上随导航照片发群
· 回复里「15:00-18:00」是活动时间，家长可能误当成集合时间，被追问要主动区分
· 家长连问集合信息，说明在做行程安排；若活动前 2 天仍未定，建议先给个大致时段
```

这一段的价值在于：**它把「我不知道」变成了「你该怎么做」。**
同样一次调用，家长拿到的是诚实，客服拿到的是下一步动作。

**这也是我在这轮里学到的东西**：模型应用的性能瓶颈，往往不在模型，
在「有没有把正确的话，说给正确的人」。

## 打不开 / 报错怎么办

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `AttributeError: module 'xxx' has no attribute 'yyy'` | **进程还是旧代码**。Streamlit 只重跑入口脚本，已经 import 的模块留在内存里不会重新加载 | 关掉黑色启动窗口，**重新双击 `启动工作台.bat`**（现在界面会自动提示这句） |
| `Port 8501 is already in use` | 上一次的窗口没关干净 | 任务管理器结束 `python.exe`，或换端口 `--server.port 8502` |
| `❌ 未找到 DEEPSEEK_API_KEY` | `.env` 没配 | 界面「🔑 API 设置」里填 Key，点保存并测试 |
| 页面能开但一问就报 `连不上` | Key 错 / 地址少 `/v1` / 模型名不配套 | 看「保存并测试连接」的报错，按三样依次查 |

改完任何 `.py` 文件之后，**都要重启一次**——这是 Streamlit 的机制，不是 bug。

## 已知限制

- **只存当前这一期**：一期办完，把新推文粘进来就**整条替换**成新一期（推文没写到的字段会清空，
  不继承上一期），旧记录进 `data/archive/superseded.jsonl`、旧推文进 `data/archive/article_<期次>.md`，
  外加 `data/backups/` 的整文件快照。往期只留档，系统不回答「上期多少钱」——按业务需求这是对的
  （两期活动不会同时办）。**例外是活动回顾推文**：它按期次长期存在 `data/articles/reviews/`，
  客服点到期次时会把那一期回顾原文附进上下文
- 集合点导航照片只能占位提醒（图片无法自动生成）；现场亮点与回顾细节现在是**按原文拟初稿 + 客服核对**，
  找不到可验证的推文原句时宁可留占位符
- 回顾推文链接没写在推文原文里时仍需人工补（能从原文里抽到就自动填）
- 「海南大学」公众号没有可分享链接，必须客服手动发名片
- 盲测集只有 10 条且已被污染，不足以证明泛化能力（见上文「评测」）
- 尚未接入 FastAPI（后端接口框架）/ 流式输出 / 多轮上下文压缩

## 一条自我约束

这个工具给人用，说错一句就是客服发错一条消息。所以做的时候定了一条规矩：

> **能确定的事交给代码，不确定的事宁可说「没有记录」，也不要让模型去猜。**

具体体现：价格和名额不靠模型猜，而是从结构化字段里取；
字段缺失一律留 `null` 而不用附近期次顶替；文案里缺的值保留 `{{占位符}}` 让客服去问；
被问到自己不知道的信息时，回答「这边没有查到，我确认后回复您」，而不是给一个像样的答案。
