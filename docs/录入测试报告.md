## 三、修复与决定

### ① 存储模型改成「单活动」——期次这个概念撤掉了

**测试中发现的隐患**：客服在改第十六期，顺手把第十七期的推文粘进来，
`S16` 整条记录被换成了第十七期的内容（标题、日期、名额全变）。

**一开始我的做法是加护栏拦下它。后来这个做法被否掉了**，因为需求不是这样：
一期活动办完才办下一期，两期不会同时进行，**已经办完的活动根本不需要再查**。
所以「粘新推文」本来就应该是**正常的新建方式**——把当前那条覆盖成新的。

现在的模型：

| | 以前 | 现在 |
|---|---|---|
| 存储 | 文件里存 4 条活动，按 S16/S06/S04/S01 索引 | **只存 1 条，就是正在办的那一期** |
| 换新一期 | 需要 `create_activity`（一直没做） | **直接把新推文粘进来，覆盖当前那条** |
| 往期 | 可查询 | 移到 `data/archive/past_activities.json`，只留档、不查询 |
| 期次选择器 | 界面下拉框 | 已删除 |
| 跨期护栏 | 拦下别期内容 | 已删除（没有「别期」这回事了） |

**安全兜底没丢**：每次写入前 `store` 自动备份到 `data/backups/`，
覆盖错了能从备份里捞回来。

**顺带的好处**：`create_activity` 这个一直卡着的硬缺口自动消失了——
新建一期 = 覆盖当前一期，不需要新功能。

### ② 每条回复都在罗列缺项（干扰）

**现象**：几乎每条回复都带一句「其余集合地点、集合时间、是否分组、每组人数尚未填写」。

**根因**：生成确认语时，我把缺项清单喂给了模型，它就照抄一遍。

**修法**：不喂清单，明确要求「不要罗列还缺哪些字段，界面右侧有实时面板」。
现在回复长度：

| 场景 | 修前 | 修后 |
|---|---|---|
| 录入室外 | 60+ 字（含 4 项缺项清单） | 17 字：「已成功录入：室内外类型为"室外"。」 |
| 自我更正 | 60+ 字 | 11 字：「已按"室内"成功录入。」 |

### ③ 换期时静默串期（不报错，最危险）

**现象**：粘进另一期的推文后，推文里没写到的字段（集合地点、集合时间、名额、室内外、分组人数）
仍然沿用上一期的值。界面看起来「字段齐全」，实际每一格都可能错了一期。

**根因**：`store.update_activity()` 只有一种写法 `target.update(accepted)`，
即「只覆盖这次给的字段」。这在补信息时正确，在换期时把上一期的值静默留下。
判断层也从来没回答过「这是不是**另一期**」，只判了 `kind` 和 `is_article`。

**修法**：拆成两套语义。

| 模式 | 触发 | 行为 |
|---|---|---|
| 合并 `replace=False` | 同一期补充/更正、单句改字段 | 只覆盖这次提到的字段 |
| 替换 `replace=True` | 另一期的推文 | 空白记录 + 只留抽到的字段，其余清空 |

判定「是不是另一期」取两路并集：代码比 `session_label`（最可靠）+ 模型 `is_new_activity`（兜住没写期次的推文）。
替换时额外：清空白名单外旧字段（`capacity_text`/`source`/`_*_note`）→ 按新期次重算 `id`/`session_no`
→ 旧记录进 `data/archive/superseded.jsonl` → `status` 默认「待确认」不继承「报名中」。

**测试怎么防它回来**：`write_tests.py` 里加了 11 条**不走模型**的纯代码断言
（`store_replace_tests()`），直接调 `update_activity(replace=True)` 检查磁盘结果。
这条纪律不能靠模型心情，所以不写成端到端用例。

## 四、现在这套录入是怎么分工的

```
客服打一句话
     ↓
① classify_input()          ← 模型判断：这是补充信息，还是在提问？
     ↓ update                    ↓ question
② 代码校验字段白名单            把这一期资料给模型，直接回答
     ↓
③ store.update_activity()   ← 字段校验 + 写前备份
     ↓
④ 模型说一句确认（不罗列缺项）
     ↓
右侧状态面板由 store.missing_fields() 重算并刷新
```

**没有一行关键词表。** 判断归模型，纪律归代码（白名单、校验、备份）。

```bash
.venv\Scripts\python.exe eval\write_tests.py
```

`store.DATA_DIR`、`store.BACKUP_DIR` 一起指过去，**永远不碰 `data/activities.json`

## 七、2026-10-26 加的两组断言

用户报了三个问题（进校预约没发出来 / 收尾文案要按推文生成 / 回顾推文要存起来），
都落在「文案产出」这条链上。补了下面这些断言，**全部是纯代码、不走模型**，
因为它们要守的是纪律，不是模型判断：

### A. 群文案渲染（14 条）

| 断言 | 抓的是什么 |
|---|---|
| 阶段② 的 5 条标签序列必须完全对 | 「引用了流程但没把流程发出来」——只输出门禁提醒，其余四条静默丢失 |
| 阶段② 里手动发送项恰好 2 条 | 公众号名片、填写示例图被漏标 |
| `.env` 的被访人姓名/电话填进文案 | 占位符没接上数据源 |
| 清空 env 后保留占位符并进未填清单 | 「查不到就当空字符串」导致发出去一句「被访人：」 |
| `{{反馈时点}}` 永远进未填清单且带原因 | 照抄默认值，建群晚的活动来不及催审核 |
| 5 个阶段都不许有**未申报**的模板残留 | 整类「静默丢数据」 |
| `only_tags` 能把「结束感谢」和「回顾分享」分开 | 客服只要一段，却给了两段，其中一段全是空占位符 |
| 传 override 就能覆盖「必须人工」的占位符 | 拟稿填不进去 |

### B. 回顾推文存储（13 条）

| 断言 | 抓的是什么 |
|---|---|
| 期次识别（含中文数字归一） | 「第九期」和「第9期」存成两份，查的时候漏一份 |
| 按期次命名 + 重存先备份 + 索引去重 | 覆盖掉旧稿且找不回来 |
| 从回顾推文里抽出公众号链接 | 「回顾推文链接」永远得人工填 |
| **存回顾推文不改动活动记录** | 回顾里全是上一期的旧值，抽字段就串期 |
| 模型误判时，代码用反向硬标记否决 | 判成「推广推文」会**覆盖当期推文**；判成「回顾」只多存一个文件 |

### 实测抓到的一次真事故

加完断言第一次跑，那条「粘回顾推文」的用例是红的：

```
❌ 粘回顾推文 → 存成 （没存）
   调用链 ['classify', 'update_activity']
   活动字段变化：{'location': '海南大学', 'grouping': '分组', 'group_size': '5组'}
```

模型把整篇回顾推文判成 `is_article=false`，于是掉进录入分支，
把回顾里的旧地点写进了**当前这一期**——而且它把「分成五个小组」抽成了「5人一组」。
不是猜出来的风险，是当场复现出来的。
所以现在 `is_article` 也接受代码旁证的纠正，不再只信模型。
