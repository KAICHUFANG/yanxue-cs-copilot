# 犯错笔记（这个项目踩过的坑，按类型归档）

> 目的不是记流水账，是**每一条都变成可执行的检查动作**。
> 下次动手前扫一眼「检查方法」那一列，比记住教训更有用。
>
> 时间跨度：2026-10-22 ~ 2026-10-30。全部是真实发生过的，没有假设。

---

## A. 需求理解类（最容易重犯，因为每次场景都长不一样）

### A1. 按「你提的那个功能」改，而不是按「这个事实出现在哪」改

**现象**：你让我改「导航图什么时候发」。我改了流程清单、改了发定位文案，就回复完成了。
结果你问「有导航图吗」，系统还是答「活动前一天晚上发」。

**根因**：同一个事实（导航图何时发）散在 **5 处**：
`policies.nav_photo_policy`、① 欢迎语、③ 导航照片手动项、③ handler_todo、④ 出发提醒。
我按「功能」去找，只找到 2 处。

**检查方法**（以后每次改口径必做）：

```bash
# 改任何「口径类」的东西之前，先把所有表述捞出来
grep -rn "关键词" data/*.json docs/*.md *.py | grep -v ".venv"
```

**判断标准**：改完要能说出「这个词/这个事实一共出现在 N 处，我改了 N 处」。说不出 N 就不算完。

### A2. 按「存放在哪」分组，把不相关的东西凑一起

**现象**：被访人姓名/电话出现在「🔑 API 设置」面板里。你问「为什么受访人信息在 API 设置里」。

**根因**：它们都存在 `.env` 里，我就按「都是 .env 的东西」分组了。
但 `.env` 只是**存放位置**，不是功能分类——API Key 是部署凭据，被访人是业务信息。

**检查方法**：摆放任何输入项之前问一句「用户会去这里找它吗」。
如果答案是「不会，得先知道它存在」，那分组就错了。

### A3. 把「系统能做什么」当成「客服想做什么」

**现象**：做了「生成全部群文案」按钮，一次吐 5 段正文 + 一堆「需人工补」。
你最后说这个按钮改成「显示发布流程」就行。

**根因**：我按「代码能一次渲染完」做功能，没想「客服拿到 5 段混着占位符的文案，
该先发哪段、哪段现在还发不出去」——等于把判断成本转给了她。

**检查方法**：给客服做功能时问「她拿到这个东西的第一秒要做什么决定」。
如果答案是「她得自己判断」，说明这个功能该拆或该换形态。

## B. 提示词 / 规则匹配类（共同特征：时好时坏）

### B1. 提示词的输出约束里漏了一个合法值

**现象**：「生成预约进校文案」有时正确、有时吐成「欢迎语」。同一句话连问 4 次，2 对 2 错。

**根因**：分类提示词最后的 JSON 结构里写的是
`"stage": "欢迎语/活动提醒/出发提醒/结束感谢"` ——**漏了「进校预约提醒」**。
正文说明里提过它，但输出约束里没有这个值，模型只能在四个里挑。

**检查方法**：任何「受约束的输出」（枚举、JSON 结构），把**代码认识的所有值**与
**提示词里列的所有值**对一遍。两边不一致就会时好时坏。

### B2. 关键词匹配的顺序决定了结果

**现象**：「写个当天的出发提醒」被渲染成 ③ 活动提醒（应该是 ④）。
因为这句话同时含「提醒」和「出发」，而 `("提醒","③")` 排在 `("出发","④")` 前面。

**检查方法**：有多关键词映射表时，**具体的说法必须排在笼统的之前**，
并且为每条说法写一条断言（我后来补了 14 条）。

### B3. 无条件注入「可能不成立」的规则

**现象**：集合点已经填好了，系统还答「集合点每期不一样，定了我发您」——自相矛盾。

**根因**：`meeting_point_policy` 那句「集合点每期不同，确定后发定位」是**无条件**进上下文的。
它成立的前提是「集合点还没填」，但这个前提没被检查。

**检查方法**：每条 policy 问一句「它在什么情况下不成立」。
不成立时要么加 `applies_when_empty` 条件，要么改成条件式表述。

### A4. 机制做对了，但业务概念理解错了

**现象**：我按「导航图 = 帮家长找路的辅助」去写文案，输出听起来很顺：
「导航图我会在活动开始前半小时发到群里，帮您确认从哪个门进、车停哪」。
你说这是搞错概念——**导航图是为了找到精确的集合位置**（哪个入口、车停哪一片、集合点在园内哪儿），
「怎么过去」由定位解决；而且**只有集合点难找时才需要**它。

**根因**：我把「导航图」当成了「路线图」。概念错了，字段、机制、状态判断全都对，
文案照样是错的——而且因为读起来通顺，很难被自己发现。

**检查方法**：凡是业务名词（导航图、引导图、定位、接龙、同行价），
先问一句**「它解决的是谁的什么问题」**，再问「什么情况下不需要它」。
两个答案都能说清，才算理解了这个词。
**这个概念我错了两次**，第二次更隐蔽：
- 第一次：说成「指路」（从哪个门进、车停哪一片）
- 第二次：改完还是带着「车停哪一片」——因为我把「找精确位置」和「停车」混在一起了
- 正确定义：**一组沿步行路线拍的引导照片**，给**人走**用，从门口一路拍到集合点

两次都错在「没问它服务的是谁」：导航图服务的是**步行到集合点的家长**，
而「车怎么进校、停哪儿」是**进校门提醒**的事，两件事被我揉在一起了。

**同类风险**：这类错误测试也挡不住（测试只能验措辞，验不了概念），
只能靠把定义写进数据（`nav_photo_policy.note_for_model`）并让用户复核。

**一句话判据**：讲任何业务名词前，先说清「**谁在用、怎么用、什么情况下不用**」，
三者齐了再写文案。

## C. 数据一致性类（不报错，只会静默不一致）

### C1. 能算出来的东西不要存

**现象**：`weekday` 手填，日期改了星期没改 → 文案里出现「10月25日（周六）」。

**修法**：`weekday / duration_minutes / session_no` 不落盘，读时算、写时摘。

**检查方法**：新增字段时问「这个值能不能从别的字段算出来」。能，就不要存。

### C2. 同一份内容存两处（文档 vs 数据）

**现象**：`docs/活动群文案流程.md` 里手抄了 8 条文案，改了数据文档就是旧的。

**修法**：文案原文只留在数据里，文档由 `tools/gen_copy_doc.py` 生成。

**检查方法**：凡「生成物」都要有断言盯着它是否过期（我加了「生成的群文案原文.md 收录了全部模板」）。

### C3. 无条件备份 = 垃圾堆积

**现象**：`data/backups/` 446 个文件 7.3 MB，其中 302 个字节完全相同，最多一组重复 118 份。

**修法**：按内容哈希去重 + 只留最近 60 份。**注意默认参数陷阱**：
`def f(keep=BACKUP_KEEP)` 在定义时就绑定了值，改模块变量无效（这是测试当场抓到的）。

### C4. 文件名只到「秒」

**现象**：同一秒内保存两次回顾推文，备份互相覆盖，静默丢一份。

**修法**：文件名带内容哈希。

## D. 测试类（最危险：测试自己制造事故）

### D1. 测试污染真实数据

**现象**（两次）：
① 只隔离了 `ACTIVITIES_FILE`，没隔离 `DATA_DIR` → 测试把真实推文冲掉了（靠 git 恢复）。
② `run_eval` 同样只隔离一半 → `archive/superseded.jsonl` 被追加了一条
「整条替换为 第九十九期」的测试垃圾。

**检查方法**：任何会走写库路径的测试，**必须同时隔离**：
`config.DATA_DIR`、`config.DATA_FILE`、`store.DATA_DIR`、`store.BACKUP_DIR`。
验证方式：跑测试前后对 `data/` 取 sha1，必须一致。

### D2. 测试之间互相污染

**现象**：跑完全套，`data_hygiene` 里「没有回顾推文」这个前提不成立了——
因为前面的 `copy_layer_tests` 往测试副本里存了一份回顾推文。
同类问题：`data/logs` 里的真实记录被 copytree 带进副本，导致「恰好 1 条」的断言失败。

**检查方法**：破坏性/前提型的用例，**先清目标目录再断言**，别依赖「测试开始时是干净的」。

### D3. 测试写死了业务里的具体值

**现象**：用例里写 `render_group_messages("S18")`，但测试副本跑的是冻结题库（`S16`）→ `KeyError`。

**检查方法**：测试里不要出现真实期次/路径；一律从 `knowledge.get_activity()` 取。

### D4. 冻结输入不完整

**现象**：Q27「谁带队」突然连续报红，答案是「某位老师带队」。
根因：题库冻结了 `activities.json`（第十六期），但 `article` 指向 `articles/current.md`
（已换成第十八期）。混合上下文里，模型读到文末「审核丨某老师」，就把**署名当成了带队人**。

**检查方法**：冻结要冻结**所有影响答案的输入**。判断标准：删掉/换掉它，答案会变吗？会就得冻。

## E. 环境 / 平台类（和业务逻辑无关，但一样会炸）

| # | 现象 | 根因 | 检查方法 |
|---|---|---|---|
| E1 | `AttributeError: 模块没有属性` | Streamlit 只重跑入口脚本，已 import 的模块不重载 | 改完 `.py` **必须重启进程**；已加 `CODE_VERSION` 自检 |
| E2 | 新实例没起来，改的代码看不到 | 端口被上一个进程占着，`Port 8501 is not available` 被忽略 | 重启前先 `netstat` 看端口；看启动日志第一行 |
| E3 | 打开就崩 `Missing credentials` | openai 3.x **构造时**校验凭证，而客户端在 import 时创建 | 占位串兜底；依赖钉主版本 |
| E4 | `pip install` 崩 `UnicodeDecodeError: gbk` | `requirements.txt` 里写了中文注释，pip 用系统区域编码读 | 依赖文件**保持纯 ASCII** |
| E5 | `.bat` 里中文被咬坏、报 `'内，不动…' is not recognized` | UTF-8 的 bat + `chcp 65001` 会切错多字节字符 | bat **纯英文**，中文放 `.txt` |
| E6 | 路径显示少了反斜杠 | `st.error` 走 Markdown，`\.` 被当转义符 | 路径用 `st.code` 或纯文本块 |
| E7 | 复制 `.venv` 给别人用不了 | venv 不含解释器本体，`pyvenv.cfg` 指向你的机器 | 用便携版（内置 Python）或让对方自建环境 |

## F. 我（助手）反复犯的三个习惯性错误

1. **改完就宣布完成，没有回头 grep「这个事实还有没有别处」**（见 A1）。
2. **把「代码能跑通」当成「需求满足了」**（见 A3、C1）。
3. **测试写得太顺手，忘了它是会写盘的**（见 D1、D2）。
   我的测试跑得比人快，所以它更容易撞出生产上才会发生的事故——
   这次就是这样抓到「同一秒备份覆盖」的。

## G. 2026-10-30 按本笔记审计出的 6 个漏洞（留存证据）

审计方式：把笔记当清单，逐条用**命令**验证（不靠眼看）。结果 6 个问题，其中 2 个高危。

| # | 漏洞 | 属于哪条笔记 | 教训 |
|---|---|---|---|
| H1 | **便携包整体过期**：7 个关键文件哈希全不一致，客服拿到的是「导航图=车停哪 / 一键生成全部文案」那一版 | C2 生成物会过期 | 手工同步的东西一定会过期。生成物必须有构建脚本，且构建后要**比对哈希**，不能凭「我记得同步了」 |
| H2 | **集合点为空也能生成「发定位文案」**：文案第一句固定是「刚把集合点定位发群里了」，可那时她根本还没发过 | A3 跑通≠需求满足 | 文案里的**每一句断言都要有数据前提**。有「我做了 X」这种话，就要检查 X 的前提字段 |
| M1 | 提示词 stage 枚举缺 5 个别名（拉群/建群/当天早上/回顾/前一天） | B1 枚举漏值 | 枚举要**双向核对**：提示词里列的 vs 代码认识的 |
| M2 | 「位置」类说法进不了发定位链路（只认「定位」） | A1 按关键词而非意图 | 抓意图时要把用户的**所有说法**列出来，不能只抓一个词 |
| M3 | 面板说「信息齐全」，一问文案却被拒 | A3 判断成本转给客服 | 「条件缺项」要和「必填缺项」分开显示，不能只显示后者 |
| L | 测试写死期次；dev 启动 bat 含中文 | D3 / E5 | 老问题又犯一次——**说明检查清单要真的每次跑** |

### 最值得记的一个：串期判定被自己挡住了

审计中途，「粘贴第十七期推文」那条用例报错：`整条替换判定：False`，
但 `session_label` 明明从第十六期变成了第十七期，上一期的 `pricing` 留在了新一期里。

```python
# 旧代码（错）
if not decided.get("is_article"):
    return False                      # ← 模型说「不是文章」就直接返回了
if new_label != old_label: return True # ← 这条最可靠的信号被挡在后面
```

注释写着「两条**独立**信号，任一成立就算另一期」，但实际是**串联**的。
模型只要判错 is_article，代码这路最可靠的服务就废了 → 静默合并 → 数据错一期。

**判据**：「两条独立信号取并集」这种设计，写完要检查**它们是不是真的并列**。
只要有一个 `return` 挡在中间，就不是并集。

### E8. 变量有「两个来源」，而程序不告诉你用的是哪个

**现象**：便携版没有 `.env`，却不用输入 Key 就能用。用户当场反问「搞什么啊」。

**根因**：`config.py` 用 `os.getenv("DEEPSEEK_API_KEY")` 读 Key。
Windows 的**用户级环境变量**会被每个新进程继承，所以：

```
没有 .env → os.environ 里那个变量生效 → 静默用掉一个你早就忘了的旧 Key
（实测：系统变量是 sk-03ad1…，而他 .env 里是 sk-abb45…，两者不是一个）
```

**三个后果**：改 `.env` 不生效；换机器就没了；**客服电脑上若残留别人的同名变量，会静默用掉别人的 Key**。

**修法（三层）**：
① 启动脚本里 `set "DEEPSEEK_API_KEY="` —— 只认本文件夹的 `.env`
② `config.KEY_SOURCE` 记录来源，界面显示「来自 .env / 来自系统环境变量」
③ 来源是系统环境变量时，界面直接给黄色警告并说明怎么改

**判据**：凡是「配置有两个来源」的地方，**必须能查出当前生效的是哪一个**。
「读到了」不等于「读对了」——这次就是读到了，但读错了来源。

## 每次改完的三句话自检

1. **这个事实一共出现在几处？我改了全部吗？**（A1）
2. **哪些测试会写盘？它们隔离干净了吗？**（D1）
3. **新加的字段/枚举，提示词和代码两边都认吗？**（B1）
