# 踩坑复盘：为什么一开始用了规则路由

> **说明**：文中的 `router.py`、`eval/ab_compare.py`、`eval/ab_real.py`、`eval/check_routing.py`
> 都已经在后续重构里删掉了（架构从「多期次 + 关键词路由」改成「单活动 + 模型判断」）。
> 数据与结论保留在这里，因为它们说明的是**判断过程**，不依赖代码还在不在。

> 这份文档回答一个问题：**一个处理人类语言的系统，为什么最初会用关键词匹配判意图？**
>
> 留着它有两个用处：面试被问到时不用临场编；以及提醒自己别再用同一种方式误诊。

---

## 一句话结论

**我误诊了。** 我把「我的工具设计有缺陷」当成了「模型不可靠」，
然后用 284 行代码去补一个不存在的短板。

---

## 一、错误是怎么一步步长出来的

### 第 1 步：第一版是纯 Function Calling，表现很差

`router.py` 里还留着当时的记录：

```
前四版我们把"该调哪个工具""问的是第几期"全交给模型判断，
结果在三个错误行为之间来回摇摆：
    ① 全部反问期次   ② 全部查 S16   ③ 全部只调 list_activities
```

### 第 2 步：我做了这个推断

> 「第十六期」里的期次是**能解析出来的**，退费这个词对应哪个工具也是**确定的**。
> 把它交给概率模型，就是在用不确定的东西做确定的事。

**前半句对，后半句错。**

而且这个错误不是「该不该用规则」这么简单——它前面还有两个更早的判断已经错了：

1. 我把两件性质完全不同的事捆成了一件事（见根因一）
2. 我把模型表现差的**原因**判断错了（见根因二）

### 第 3 步：规则长出来了，而且开始自我繁殖

有了关键词表之后，每一个新的问法都是加一个词：

- 为了认「车能开进学校吗」→ 加单字「车」→ 「路上堵车」被误判成进校流程
- 为了认「怎么报名」→ 加「怎么报名」→ 「第十期怎么报名」不再如实拒答

**关键词表变成了我手写的训练集**，而且它没有泛化能力——加一个词就可能踩坏另一处。

### 第 4 步：我照着路由逻辑出了考卷

28 条回归集里有 15 条在题干里写了「第十六期」。

**这不是疏忽，是因为我编题时脑子里装的是路由逻辑。** 拿这份考卷给路由打分，
它当然接近满分——**代码在自己的考卷上考试，分数没有意义。**

---

## 二、三个根因

### 根因一：把两个决策捆成了一个

一个请求进来，其实包含两个完全不同的决策：

| 决策 | 真正的性质 | 该用什么 |
|---|---|---|
| **现在服务的是哪一期？** | 确定性——它来自界面、来自群绑定 | **状态传递**，根本不该是个「判断」 |
| **这句话在问什么？** | 语义——家长有一万种说法 | **模型** |

我把这两件事都归到了「确定性判断」下面，因为第一件确实是确定的。

**这是逻辑跳跃：一件事确定，不等于跟它写在同一行里的另一件事也确定。**

### 根因二：把自己的设计缺陷记成了模型的能力缺陷

留在代码里的原始证据，是我自己写的工具 schema：

```python
"description": "…调用前必须先确定期次编号。",
"required": ["activity_id"],        # 期次是必填项
```

家长问「多少钱」的时候，模型**根本没有合法选项**。它只有两条路：

- 反问家长「您问的是哪一期？」 → 这就是那个「全部反问期次」
- 先调 `list_activities` 再调 `get_activity` → 这就是那个「全部只调 list_activities」

所以那三个所谓的「错误行为」，**不是模型笨，是我的 schema 逼出来的**。

正确的修法只要两行：`activity_id` 改成可选、「当前活动」放进上下文。
这两行 v3 里已经有了。

### 根因三：一次证据误用

当时还有一个自以为是的「铁证」：实测 DeepSeek 会忽略 `tool_choice` 的强制指定。

但这是**两件不同的事**：

| | 含义 |
|---|---|
| `tool_choice` 被忽略 | 我**不能强迫**模型选某个工具 |
| 模型选错工具 | 模型**选得不对** |

我用前者证明了后者，再推出「所以我自己来选」。**这个推理链中间断了一环。**

## 三、数据是怎么打脸的

拿到真实家长聊天记录之后，第一件事不是看分数，是看输入长什么样：

| 来源 | 条数 | 提到期次的 |
|---|---|---|
| **真实家长聊天记录** | 10 | **0 条（0%）** |
| 我自己编的回归集 | 28 | 15 条（54%） |

真实提问的样子：

```
车不能进学校吗？如果预约的时候写了车牌号
我能晚一点过去么，周六还有个课要到3点半结束
请问这个怎么报名，是要在群里接龙吗？
集合地点在哪里？
事先分好组吗？一组几人？
1.集合地点在哪里？2.事先分好组吗？3.研学地点都在海大里面吗？4.如果下暴雨怎么办？
```

**群就是第十六期的群。家长只会问「多少钱」，不会说「第十六期多少钱」。**

### 这里最该记住的一条

我第一次盲测跑出 **7/10**，反应是去看那 3 条失败的题、改关键词。

但那批数据真正在说的不是「7/10 不够好」，而是：

> **10 条真实家长提问，一条都没提期次。**

我当时盯着分数，没看输入分布。

**一个评测集最大的价值不在通过率，在它长什么样。**

## 四、四个架构的实测对比

发现问题是第一步，决定怎么改需要数据。所以我把四种做法在同一批 28 条用例上跑了一遍
（`eval/ab_compare.py`，`temperature=0`）：

| 架构 | 做法 | 通过率 | 平均延迟 | 总 tokens |
|---|---|---|---|---|
| A 规则路由 | 关键词判意图 → 代码执行工具 | 28/28 | 1.46s | 74k |
| B 模型选工具 | 删掉 router，模型从 8 个工具里自己挑 | 25/28 | 2.33s | 148k |
| C 全量投喂 | 不用工具，知识库全文塞进上下文 | 22/28 | **1.15s** | 279k |
| D 读写分离 | 写入走工具，其余全量投喂 | 27/28 | 1.39s | 269k |

- **B 更慢、更贵、还更差** → 「把判断全交给模型」不是答案
- **C 最快但不能写库** → 缺了确定性操作，光靠上下文不行
- **D 分数接近但要 3.6 倍 token** → 方向对，但还没到位

B 输得最值得看。它的失败不是「选错工具」，而是**选错知识源之后开始圆场**：

```
家长：需要带身份证吗，我看要填身份证号
B   ：不用带身份证原件，报名表里填身份证号是为了买保险用的…
      ↑ 知识库里写的是「不需要，登记也不填身份证号」。它没查到，就编了个合理的理由。
```

## 五、v3 的正解：期次由上下文给定，不从话里猜

把「猜」换成「给定」，路由整层就消失了：

```
当前活动 = S16（界面上选中的那一期 / 群绑定）
        ↓
knowledge.build_context()
    这一期的数据 + 全部期次概要 + 跨期通用规则 + 流程定稿 + 文案模板
        ↓
模型直接读这段上下文回答
    没有工具、没有意图分类、没有期次正则、没有关键词表
```

**确定性的事不经过模型**：

| 功能 | 做法 |
|---|---|
| 问答（读） | 模型读上下文直答 |
| 信息录入（写） | `store.py`：字段白名单 + 类型校验 + 写前备份 |
| 文案生成 | `renderer.py`：占位符填充，原文输出 |
| 缺口体检 | `store.missing_fields()` |

**结果**（`eval/ab_real.py`，23 条真实家长问法，全部不带期次）：

| | 通过率 | 每条约 tokens |
|---|---|---|
| v2 关键词路由（284 行） | 23/23 | 约 2.6k |
| **v3 上下文直答（0 行路由）** | **23/23** | 7.1k |

打平。但 v3 少了 284 行路由代码、9 张关键词表、3 个期次正则，
以及那套「加一个词就踩坏另一处」的维护负担。

**代价也要讲清楚**：v3 每条多花约 3 倍 token，而且**不随规模扩展**——
知识库现在 1.4 万字，到 30 期会撑爆上下文窗口，那时唯一的解是 RAG（检索增强生成）。
所以 v3 是当前正确的解，不是永久解。

## 六、可复用的判据

以后遇到「这句话该怎么处理」，先把决策分三类，别混着做：

| 类型 | 例子 | 用什么 |
|---|---|---|
| **状态** | 现在服务第几期、谁在问、哪个群 | 传进来（界面/群绑定/配置文件），**不推理** |
| **语义** | 这句话在问什么、有没有隐含情绪 | 模型 |
| **确定性变换** | 金额格式、字段校验、占位符填充、写前备份 | 代码 |

判断口诀：

> **输入是人类语言 ≠ 每一层都要做语义理解。**
> **但也 ≠ 每一层都能用规则。**
> 关键是逐个决策问：它是状态、是语义、还是变换？

以及一条数据纪律：

> **评测集要按需求长出来，不能按代码长出来。**
> 出题时先问：真实用户会这么说话吗？这个需求真实存在吗？

## 七、面试被问到时怎么讲

如果面试官问「你为什么一开始用规则路由」，别答「一开始不懂」。答这个：

> 我误诊了。项目第一版是纯 Function Calling，模型表现很差，一直在反问期次。
> 我当时判断「期次解析是确定性的，不该交给模型」，于是加了规则路由。
>
> 但回头看，模型反问的真实原因是我把 `activity_id` 设成了必填——**它没有合法选项**。
> 我把自己的 schema 缺陷记成了模型的能力缺陷。
>
> 后来拿到真实家长聊天记录，发现提问里期次出现率是 0%，规则路由在解决一个不存在的问题。
> 我做了四种架构的对比实验，最后改成：期次由界面上下文给定，语义全部交给模型。
> 23 条真实问法 23/23，路由代码从 284 行变成 0 行。

这个答案的价值不在「踩过坑」，在于：**它会回头看自己的判断，而不是说「当时技术就这样」。**

## 八、最危险的一类 bug：不报错的错

规则路由那一轮，错误是**响亮**的——答非所问，客服一眼能看出来。

后来这个不一样。现象是用户贴了一句：

> 输入新活动的推文后好像只会覆盖推文中有的信息，推文中没提到的信息还是沿用的上一期的

复现出来是这样。库里原本是第十六期：

```
session_label  第十六期
meeting_point  五教104       ← 客服手工补的
meeting_time   15:00
capacity       25
```

粘进第十五期的推文（推文里**没有**集合点、集合时间、名额数字，只有「名额：每期有限，报满即止」），
跑完变成：

```
session_label  第十五期      ← 期次换了
meeting_point  五教104       ← 还是上一期的
meeting_time   15:00         ← 还是上一期的
capacity       25            ← 还是上一期的，而且推文明明没写数字
```

**每一项都长得像正常数据**。界面右侧的缺口面板显示「字段齐全」，
客服照着答「集合在五教104，名额25人」，家长去错地方、白排队。
没有任何报错，没有任何告警，数据文件也不脏——只是每一格都错了一期。

### 根因不是模型，是存储层的语义只有一种

```python
target.update(accepted)     # 只覆盖这次给的字段
```

这一行在「客服补一句『集合点改到五教104』」时完全正确，
在「客服粘一整篇新一期推文」时是错的 —— **同一段代码被当成两种意图用**。

判断层当时也没帮上忙：它只判 `kind=update` 和 `is_article`，
从来没回答过「这是不是**另一期**」。

### 修法：把「补」和「换」拆成两种语义，判定用两路信号取并集

```
replace=False  合并：只覆盖这次给的，其余不动      ← 同一期的补充/更正
replace=True   替换：空白记录 + 只留这次给的       ← 另一期的推文
```

判定「是不是另一期」不用单一信号：

| 信号 | 覆盖 | 失效场景 |
|---|---|---|
| 代码比 `session_label` | 期次是固定字段，最可靠 | 推文没写期次 |
| 模型 `is_new_activity` | 兜住没写期次的推文 | 可能把「同推文重发」误判成新一期 |

两个取**并集**。单独任何一个都会错，合起来才稳 ——
代码那一路能推翻模型，模型那一路补上代码看不见的。

### 三条可复用的判据

1. **凡是「一个函数承担两种意图」，迟早出事。** 两种意图的操作后果差得越远（覆盖 vs. 清空），
   越要显式分成两个入口，别靠参数缺省值猜。
2. **模型判「是什么」，代码判「怎么存」。** 让模型输出 `is_new_activity` 是让它理解语义；
   但「另一期就必须清空」这条纪律写死在 `store` 里，模型改不了。
3. **破坏性操作必须留可检索的痕迹。** 只靠 `backups/` 的时间戳文件不够——
   换期之后想找回上一期的推文，得一个个打开猜。现在旧记录进
   `archive/superseded.jsonl`（一行一条），旧推文进 `archive/article_<期次>.md`。
   命名带期次，人一眼能找到。

## 九、「引用了流程」不等于「把流程发出来」

用户报的现象很朴素：

> 这五个群文案有问题，首先没有发进校预约流程

不是答错，是**少了一整段**。系统给出的进校预约那段只有一条「进校门小提醒」。

### 根因：一行「有就不展开」的判断

群文案的阶段② 在 `group_messages.json` 里长这样：

```json
{
  "stage": "② 活动前 1 天早上 · 进校预约",
  "uses_process": "campus_booking",          ← 点名引用流程
  "messages": [ { "type": "reference", ... } ] ← 只自带一条门禁提醒
}
```

渲染器的写法是：

```python
if not st.get("messages"):        # ← 这一行
    if st.get("uses_process"):
        out.append({"note": "该阶段引用流程 …"})
```

**「自带文案为空」才去展开流程。** 阶段② 自带了一条门禁提醒，于是不为空，
于是 `uses_process` 被静默跳过——预约文案、公众号名片、填写示例图、催办话术四条全丢。

那条门禁提醒是 `reference` 引用，反倒能正常解析出来，所以输出看起来「像那么回事」，
客服只会觉得「系统好像漏了点什么」，而不是「这功能坏了」。

### 这类 bug 的共同形状

| 特征 | 本例 |
|---|---|
| 不报错 | 渲染成功，JSON 合法 |
| 不空 | 有一两条内容，界面不会提示「缺数据」 |
| 缺的部分看起来像「本来就没有」 | 客户以为是流程还没写 |

和第八节的串期是同一类：**数据在，代码不去取**。

### 修法：把「引用」当成待展开的清单，而不是一条提示

1. `uses_process` 一律展开成流程里的 `send_package`，并按 `seq` 排序；
2. 阶段自带的文案用 `insert_after_seq` 声明插在第几件之后发
   （门禁提醒插在「填写示例图」之后、「催办」之前）；
3. 流程里的 `handler_tips` 一起带出来，变成给客服的「这一步必须人工做的」；
4. 流程文案里的占位符同样走「查不到就申报」：`{{被访人姓名}}` / `{{被访人电话}}`
   从 `.env` 注入，`{{反馈时点}}` 永远标成必须人工改并写明怎么改。

### 加了一条防回归的断言

纯代码测试（不走模型）里现在有两条：

- 阶段② 输出的 5 条的**标签序列**必须完全等于约定顺序；
- **任何渲染结果里残留的 `{{}}` 必须在未填清单里申报过** ——
  这一条能一次抓住「静默丢数据」的整类问题，包括以后新加的模板。

## 十、让系统「按推文拟稿」时，怎么防止它编

用户的要求很合理：

> 活动圆满结束的内容让 agent 通过活动推广推文里的信息直接生成；
> 活动回顾推文直接让 agent 读活动回顾推文生成，回顾推文要存起来供查询

但这是**模型写内容**，而这段内容要发到几百人的家长群。所以加了三道闸：

| 闸 | 做法 | 挡住了什么 |
|---|---|---|
| ① 只给原文 | 只用推文原文当资料，不塞别的上下文 | 从活动字段里「顺」出推文没写的东西 |
| ② 要它交依据 | 让它同时输出「依据的原句」，**这句必须在原文里找得到**（去空白标点后子串匹配），找不到整条作废 | 编环节名、张冠李戴到往期内容 |
| ③ 拟稿要标注 | 输出里单独标「系统拟的稿」，并附依据原句 | 客服误以为是定稿、直接发出去 |

闸② 是关键：**「引用可在原文中验证」比「提示词写严一点」可靠得多。**
它把「有没有编」变成了一个确定性的字符串检查，不依赖模型自觉。

同样的思路用在「回顾推文别把新一期写脏」：

- 存回顾推文**不动任何活动字段**（回顾里全是上一期的旧值，抽了就串期）；
- 模型判「这是推广推文还是回顾推文」，代码再用反向硬标记否决一次
  （像回顾且毫无报名信息 → 一定是回顾）；
- 连 `is_article` 也纠：实测模型会把一整篇回顾推文判成「不是文章」，
  那就直接掉进录入分支把旧值写进当前期。旁证确定是文章时就按文章走。

**判错的两条路代价不对等**，这条经验可以直接搬：
判成「回顾」只是多存一个文件；判成「推广」会覆盖当期推文。
代价差这么大时，判定规则就该往便宜的那一侧偏。

## 十一、清理冗余：删掉的每一份都有理由，留下的每一份也有

用户问「项目文件里有哪些冗余数据」，一量才发现问题不在代码：

```
data/ 共 7.47 MB，其中 7.36 MB（99%）是 backups/
代码 2881 行 ≈ 112 KB → 数据体量是代码的 68 倍
```

### 最大一块：446 个备份文件，302 个是废文件

`store._backup()` 原来是「每次写库前存一份时间戳快照」。高频写库时同一个内容会被连续存成好几份：

| 现象 | 数据 |
|---|---|
| 文件数 | 446 个 |
| 字节完全相同的文件 | 328 个，分属 26 组 |
| 最多的一组 | **118 份一模一样** |

修法两条：**按内容哈希去重**（一样就不存第二份）+ **只留最近 60 份**。
结果：446 个 / 7.34 MB → 60 个 / 0.86 MB。

### 第二类：同一件事存了两份

| 位置 | 重复情况 | 处理 |
|---|---|---|
| `processes.json` 的 `entry_gate.text` vs `ready_to_send_text` | 同一门禁规则两种措辞，相似度 62% | 只留对外定稿 |
| `send_package.order` vs `items[].seq` | 顺序说了两遍 | 删 `order`，顺序只在 `seq` |
| `warnings[]` vs 预约文案正文 | 限速 30 迈、食堂、预约明天，三句都在文案里 | 删 `warnings` |
| `activities.json` 的 `weekday` / `duration_minutes` / `session_no` | 能由 date / time_range / session_label 算出 | **不存了，读时现算** |
| `docs/活动群文案流程.md` vs `group_messages.json` | 8 条文案手工抄了两份 | 文档只留流程，原文改由脚本生成 |

最后一类最隐蔽：文档说一套、系统吐一套，客服照着文档发出去，跟系统不一致，**而且没人会发现**。
现在 `docs/群文案原文.md` 由 `tools/gen_copy_doc.py` 从数据生成，页头写死「不要手改」。

### 派生字段为什么不落盘

`weekday` 由 `date` 算、`duration_minutes` 由 `time_range` 算、`session_no` 由 `session_label` 算。
留着两份的后果不是多占几字节，是**不一致**：日期改了星期没改，文案里就是「10月25日（周六）」，
发给几百个家长群，没人看得出来。

现在读写分工：`store.with_derived()` 在**读**的时候补上，`store._write()` 在**落盘前摘掉**。

### 清理过程里被抓出来的两个真 bug

1. **`BACKUP_KEEP` 写成了默认参数** —— `def _prune_backups(keep: int = BACKUP_KEEP)`。
   默认参数在**函数定义时**求值，之后改模块变量无效，上限形同不存在。测试当场抓红。
2. **备份文件名只到「秒」** —— 同一秒内保存两次会互相覆盖，备份静默丢一份。
   测试跑得快，撞出来了；生产上「客服连点两下」一样会撞。修法：文件名带内容哈希。

> 这两个都是「测试写得太快反而抓到了生产会犯的错」。
> 反过来说：如果测试写得慢一点、或者跑一次就算过，这两个 bug 会一直躺在仓库里。
